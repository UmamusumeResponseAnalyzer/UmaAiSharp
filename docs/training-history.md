# 成功普通训练历史

`pioneer_import_capture`读取锚点之前本局的抓包前缀，把成功普通训练次数导入`TrainingTurn`。原始SQLite使用只读连接和同一读取事务；支持无非空WAL的捕获快照。

恢复逻辑：

1. 由锚点的viewer_id和single_mode_chara_id定位本局，从响应编号向前读取至开局。开局必须明确为回合1、五项执行次数为0。
2. 按request_id与endpoint配对。重复捕获须具有相同载荷和版本信息，保留最早捕获的动作位置；不同请求不会因回合或命令相同而被合并。
3. 普通指令101／105／102／103／106的result_state=2计为成功普通训练；result_state=1为失败。合宿3601..3605计入协议次数，但不增加成功普通次数。
4. 对每个带五项training_exec_info_array的中间响应核对累积执行次数，最后与锚点核对。孤立训练响应、计数跳变、未知结果、请求回合不符和冲突捕获明确拒绝或停止。

计数顺序为速度、耐力、力量、根性、智力。`null`表示历史未知，五项0表示已经明确没有成功普通训练，二者不同。导入产物保留开局／锚点编号、捕获数量、训练总数、合宿次数、失败次数和前缀SHA-256；未来响应不参加恢复或前缀哈希。

运行时通过`SuccessfulOrdinaryTrainingCounts`已知位和独占缓冲分区保存这五项次数。只有成功普通训练增加对应项；失败与合宿不增加，协议执行次数照常增加。CopyInto、精确分叉和工作区复用包含该分区；删除角色效果25不会覆盖其内容。该版本规则身份为runtime v12 / training-turn v12。

成功普通训练累计4次触发单项升级，协议次数另包含合宿和失败。执行器登记待结算升级，等级在相关事件确认时增加；当前可见事件由调度顺序决定。字段、原包窗口和执行示例见[训练升级触发](training-level-trigger.md)。

本次原包导入锚点为52989（回合37）、58275（回合30）、53109（回合50）。前两者分别恢复成功普通次数`[3,8,2,4,5]`和`[5,1,9,0,4]`；第三个前缀包含29次训练、4次合宿及1次失败。原包和master只读，输入及逐项验证见[执行记录](../artifacts/implementation/training-history-01/verify-final/verification.json)。这些窗口来自既有研究材料。

测试覆盖同请求重复捕获（包括延后重复的开局响应）、未来包隔离、缺开局／动作／结果、未知分支、不同育成、冲突捕获，以及普通／合宿成功失败的状态维护、分叉和多线程一致性。

成功普通训练计数不等于全部历史。连续事件进度、黄金船指定训练状态、临时效果生命周期、训练后／回合前事件队列，以及待升级里程碑到可见事件的调度继续接入。

## URA 中途初始化

PioneerAiPlugin 从服务端的五项训练执行次数开始追踪。全零时可以直接确定成功普通次数。中途接入时，已经收到的普通训练结果单独累计。计数出现跳变时，从新的服务端计数重新追踪，并在面板标明训练进度经过估计。

缺失的历史按训练种类和已进入的合宿期数拟合。对低于 Lv5 的训练，扣除第 2／4 次高评审的升级后，每级对应四次成功普通训练，当前等级限定剩余进度为 0–3 次。成功次数也受总执行次数与已观察结果约束。每个可行值在拟合频数上加一，再按样本抽取。同一样本在各根候选中使用相同的历史抽样。满级的成功次数不影响后续升级。

拟合沿用 `fit_turns.py` 的整局切分，只使用拟合组有完整历史且通过计数核对的训练窗口。报告单独记录留出组的窗口数量和估计误差。`pioneer_import_capture` 使用完整前缀核验精确次数。规则资源模式下，`pioneer_import_packet` 可以导入一张就绪面板，供自主执行按同一分布估计升级进度。导入报告以 `estimatedTrainingHistory` 标明；未来继承仍要求本局开局冻结的谱系。
